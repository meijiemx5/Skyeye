## 坑 1（主坑）：所有接口 403，浏览器报 "CORS 错误"

### 症状
- 打开 `https://ruianwy.site`，页面能加载，但所有数据请求失败。
- 浏览器 Network 面板显示 `statistics` / `projects` / `contracts` 等请求为 **"CORS 错误"**。
- `curl https://www.ruianwy.site/api/health` 返回 `{"Message":null}`（HTTP 403）。

### 关键认识：CORS 错误是**症状**，不是根因
浏览器报 "CORS 错误" 的真实原因是：网关返回的 **403 错误响应不带 `Access-Control-Allow-Origin` 头**，浏览器拿不到 CORS 头 → 归类为 CORS 错误。**根因是 403 本身**，不是 CORS 配置。用 `curl`（无浏览器 CORS 拦截）能看到底层真相就是 403。

### 诊断方法（逐层定位，全部只读）
关键是用 `test-invoke-method` 对比线上，做**差分诊断**：

```bash
export AWS_PROFILE=skyeye AWS_REGION=cn-northwest-1

# 1) 直接 test-invoke 方法（读取当前配置，绕过 stage 快照）
PROXY_ID=$(aws apigateway get-resources --rest-api-id mdmktte525 \
  --query "items[?path=='/{proxy+}'].id" --output text)
aws apigateway test-invoke-method --rest-api-id mdmktte525 \
  --resource-id "$PROXY_ID" --http-method GET \
  --path-with-query-string "/api/health"     # → 200 healthy ✅

# 2) 线上实际调用（走的是已部署的 stage 快照）
curl -s https://www.ruianwy.site/api/health   # → 403 {"Message":null} ❌

# 3) 排除资源策略 / WAF
aws apigateway get-rest-api --rest-api-id mdmktte525 --query "policy"   # → None
aws wafv2 list-web-acls --scope REGIONAL                                # → []
```

差分结论：

| 测试 | 走的路径 | 结果 |
|---|---|---|
| `test-invoke-method`（**当前**配置） | → Lambda | **200 healthy** ✅ |
| 线上 `GET /api/health`（**已部署快照**） | → Lambda | 403 `AccessDeniedException` |
| 线上 `OPTIONS /api/health`（MOCK，**不碰 Lambda**） | → MOCK | 403 `AccessDeniedException` |

`test-invoke` 读**当前**配置返回 200，线上读**已部署快照**返回 403 → 两者不一致。

### 根因
**`api` stage 一直在服务一份陈旧的部署快照。**

- CloudFormation 默认**只在 API 资源图变化时**才创建新的 `AWS::ApiGateway::Deployment`。
- 由于 CDK 里 API 定义从未实质变化（或某次部署中途失败、stage 未重新指向新部署），线上 stage 长期停留在**建 API 时的初始快照**（本例 `bcmfh5`，冻结于建 API 那一刻），该快照在网关入口就拒绝一切请求。
- `{"Message":null}`（大写 M）是 API Gateway 自身的拒绝响应，**不是** FastAPI 格式（FastAPI 是 `{"detail":"..."}` 小写）——据此可判断请求**没到应用**。

### 修复（外科手术，立即生效）
把**当前健康配置**重新发布到 stage：

```bash
aws apigateway create-deployment --rest-api-id mdmktte525 \
  --stage-name api --region cn-northwest-1 \
  --description "Republish current config (fix stale snapshot 403)"
```

生效后（跨区传播需十几秒到几十秒）：
- `www.ruianwy.site/api/health` → 200 healthy
- 业务接口 → `{"detail":"Not authenticated"}`（到达 FastAPI，登录即通）
- CORS 预检 `OPTIONS` → 204 + `Access-Control-Allow-Origin: *`

### 永久修复（防复发，已实现）
在 `infrastructure/lib/backend-stack.ts` 中给部署逻辑 ID 加合成时间戳"盐"：

```ts
// 强制每次 cdk deploy 都新建部署并把 stage 重新指过去，
// 使线上 stage 永远不会漂移到旧快照。
api.latestDeployment?.addToLogicalId(new Date().toISOString());
```

**副作用（预期且正确）**：此后每次 `cdk deploy` 后端都会显示变更（不再 `no changes`），每次新建一个 Deployment（旧的自动清理、不累积），部署略慢几秒。这是"永不复发"的代价。

## 坑 2：直连 execute-api 要写 `/api/api/...`（双 api 前缀）

### 症状
```bash
curl https://mdmktte525.execute-api.cn-northwest-1.amazonaws.com.cn/api/health      # → 404 Not Found
curl https://mdmktte525.execute-api.cn-northwest-1.amazonaws.com.cn/api/api/health  # → 200 healthy ✅
```

### 原因
路径里两个 `api` 含义不同：

```
.../execute-api.../ api      / api/health
                   └─┬─┘      └───┬────┘
              网关 stage 名    FastAPI 路由前缀
              (stageName)     (@app.get("/api/health"))
```

- 第一个 `api` = API Gateway 的 **stage 名**（CDK 里 `stageName: 'api'`）。
- 第二个 `api` = **FastAPI 代码里的路由前缀**（`/api/...`）。
- 直连 execute-api 域名时 stage 名计入路径，所以要 `/api/api/...`。

### 自定义域名没有这个问题
`www.ruianwy.site` 的 base path mapping 是 `(none)` → 直接进 `api` stage，**不重复**：
```bash
curl https://www.ruianwy.site/api/health       # → 200 ✅（单 api）
curl https://www.ruianwy.site/api/api/health   # → 404 ❌（多了一个 api）
```

> 澄清一个曾经的误判：排障中一度以为"execute-api 原生域名被中国区平台封锁所以 403"。**这是错的**——重新发布 stage 后，原生域名（用正确的 `/api/api/...` 路径）也返回 200。403 的真凶是坑 1 的陈旧快照，与备案封锁无关。

### 生产仍应走自定义域名
原生 execute-api 只适合**临时排障**。前端生产必须走已备案的 `www.ruianwy.site`：
1. **备案合规**：`*.execute-api...amazonaws.com.cn` 是未备案原生域名，浏览器流量存在被拦风险；整套自定义域名架构就是为绕开它。
2. **路径干净**：自定义域名是 `/api/...`，不用双前缀。

## 坑 3：前端 bundle 误连别区 endpoint（VITE_API_URL）

### 症状
仓库里残留 `frontend/.env.production`：
```
VITE_API_URL=https://npdjni0ia2.execute-api.us-east-1.amazonaws.com/api/   # ← 美国区！
```
担心中国区前端误连美国区 API。

### 实际结论：不受影响，但应清理
`deploy.sh` 中国区构建时用**命令行环境变量**注入，优先级高于 `.env.production`：
```bash
VITE_API_URL="${FRONTEND_API_BASE}" npm run build   # FRONTEND_API_BASE=https://www.ruianwy.site
```
Vite 优先级：命令行 env > `.env.production.local` > `.env.production` > `.env`。所以命令行注入会覆盖那个残留文件。

### 验证方法（查线上 bundle 实际嵌入的地址）
```bash
JS=$(curl -s https://ruianwy.site/ | grep -oP 'src="/assets/[^"]*\.js"' | grep -oP '/assets/[^"]*\.js')
curl -s "https://ruianwy.site${JS}" | grep -oP 'https://[a-zA-Z0-9._-]+' | sort -u | grep -iE "ruianwy|execute-api"
# 期望只出现 https://www.ruianwy.site ✅
```
`client.ts` 逻辑：`VITE_API_URL || 'http://localhost:8000'`——未设时才回落到本地开发地址。

### 处理
删除残留文件（它未被 git 跟踪、已被 `.gitignore` 忽略，删除无需提交）：
```bash
rm frontend/.env.production
```

## 坑 4：证书双体系（IAM vs ACM）

中国区两条链路用**不同证书体系**，同一张 `ruianwy.site`(+`www`) 证书需**导入两处**：

| 用途 | 证书体系 | 位置 |
|---|---|---|
| 前端 CloudFront | **IAM 服务器证书** | IAM（CN CloudFront 只能用 IAM 证书），id 如 `ASCARF4GALIVNP3ZRZS2J` |
| API Gateway 自定义域名 | **ACM 证书** | ACM **cn-northwest-1**（必须与 API 同区域），ARN 如 `...certificate/b8904700-...` |

- API Gateway Regional 自定义域名**不能用 IAM 证书**。
- 证书 SAN 需覆盖 `ruianwy.site` + `www.ruianwy.site`。
- ICP 备案按主域名，`www` 子域名自动包含，无需单独备案。

## 坑 5：DNS 解析确认（排除"DNS 未生效/被拦"误判）

排障时常怀疑"DNS 没生效"或"被墙"，需先用数据排除：

```bash
# CNAME 目标应等于 CDK 输出的 ApiCustomDomainTarget
cat cdk-backend-outputs.cn-northwest-1.json | grep -A1 ApiCustomDomainTarget
```

域名商解析记录应为：

| 主机记录 | 类型 | 记录值 |
|---|---|---|
| `@` | CNAME | `<CloudFront 域名>.cloudfront.cn`（前端） |
| `www` | CNAME | `d-in6izeva4e.execute-api.cn-northwest-1.amazonaws.com.cn`（API，= `ApiCustomDomainTarget`） |
| `_dnsauth` | TXT | （证书/域名验证用） |

**判断要点**：如果 `curl` 能拿到**任何** HTTP 响应（哪怕 403），就说明 DNS 已解析、链路可达——问题不在 DNS，往网关/应用层查。真正的 DNS 失败是连接超时/无法解析，不是 403。

## 完整验证清单（部署后）

```bash
export AWS_PROFILE=skyeye AWS_REGION=cn-northwest-1

# 1) stage 指向最新部署（不是初始快照）
aws apigateway get-stage --rest-api-id mdmktte525 --stage-name api \
  --query "{deploymentId:deploymentId,lastUpdated:lastUpdatedDate}"

# 2) API 健康
curl -s https://www.ruianwy.site/api/health        # → 200 {"status":"healthy",...}

# 3) 业务接口到达应用（未登录返回 FastAPI 格式 401/403）
curl -s https://www.ruianwy.site/api/projects       # → {"detail":"Not authenticated"}

# 4) CORS 预检
curl -s -D - -o /dev/null -X OPTIONS https://www.ruianwy.site/api/projects \
  -H "Origin: https://ruianwy.site" -H "Access-Control-Request-Method: GET" \
  | grep -i access-control-allow-origin              # → access-control-allow-origin: *

# 5) 前端站点
curl -s -o /dev/null -w "%{http_code}\n" https://ruianwy.site/   # → 200
```

- [ ] stage 指向部署时间 = 本次部署时间（非建 API 的初始时间）
- [ ] `/api/health` → 200 healthy
- [ ] 业务接口 → `{"detail":"..."}`（FastAPI 格式，说明到达应用）
- [ ] CORS 预检 → 204 + `Access-Control-Allow-Origin`
- [ ] 浏览器登录 `ruianwy.site`，Network 请求打到 `www.ruianwy.site/api/...` 且成功
- [ ] 附件上传/下载正常（presigned URL 指向 CN S3 桶）

## 排障速记（症状 → 先看哪里）

| 症状 | 优先排查 |
|---|---|
| 浏览器 "CORS 错误" | **先 `curl` 看真实 HTTP 码**——多半是 403 伪装成 CORS，查坑 1 |
| `curl` 返回 `{"Message":null}`（大写 M） | 网关层拒绝，请求没到应用 → 坑 1（陈旧快照，重新发布 stage） |
| `curl` 返回 `{"detail":"..."}`（小写） | 已到 FastAPI，是应用层（缺 token/权限），属正常 |
| `/api/health` 404 但 `/api/api/health` 200 | 走了原生域名，stage 名计入路径 → 坑 2，改用自定义域名 |
| 前端连错区域的 API | 查线上 bundle 实际地址 → 坑 3 |
| 自定义域名握手失败/证书报错 | 证书体系用错 → 坑 4（API 用 ACM 同区，CloudFront 用 IAM） |
| 怀疑 DNS 没生效 | 能拿到任何 HTTP 响应即非 DNS 问题 → 坑 5 |
