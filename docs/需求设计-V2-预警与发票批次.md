# Skyeye V2 需求设计（项目预警 · 报销链路 · 发票批次 · 权限收紧）

需求来源：HZY 2026-08-20 沟通记录。本文是实现前的设计基线，代码以此为准。

## 0. 需求清单与落点

| # | 需求 | 落点 |
|---|------|------|
| 1 | 项目成本分析：出库、入库完整计入项目材料成本 | `services/cost.py` + `routers/analysis.py` |
| 2 | 报销完整链路：提交报销 → 项目收款 → 创建单据 → 财务审核 → 凭证生成 → 付款 | `services/reimburse_flow.py` + `routers/reimbursements.py` |
| 3 | 权限管控：项目列表 / 合同 / 验收资料 仅管理员、项目负责人可查看 | `utils/permissions.py` + 三个 router |
| 4 | 报销环节禁止新增费用大类，只能选已有大类 | `routers/reimbursements.py` 服务端校验 |
| 5 | 项目看板预警：预算/报价/合同/验收/报销/工费/发票 缺失或逾期 → 提醒负责人 | `services/alerts.py` + `routers/alerts.py` + 工作台 |
| 6 | 发票分批次 + 一批次多张 + 材料/施工/服务不同税率 | `models/invoice.py` + `routers/invoices.py` |
| 7 | 待办中心：上班第一件事看系统有什么没做 | `/api/todos` + 待办中心页 + 顶栏红点 |

已确认的三个决策：

1. **合同权限**：严格收紧到 `admin` + `project_manager`；财务/采购改用新的精简选项接口 `GET /api/contracts/options`（只返回合同号、名称、类型、项目、金额、已付），拿不到条款/附件/发票明细。
2. **项目收款**：**硬门禁**。报销必须先确认项目收款才能创建单据；`admin` 可强制跳过，但必须填原因，写入审批日志与操作日志。
3. **预算/报价**：在 `ProjectModel` 上加金额 + 附件字段，预算金额同时用于「预算超支」预警。

AI 识别资料正确性属于下一阶段，本期不做，只做规则预警（HZY：「初步是有，下一步就是 ai 的植入」）。

## 1. 项目材料成本（需求 1）

### 现状问题

`analysis.py` 已把 `record_type in ("in","out")` 且 `project_id` 匹配的出入库都计入 `material_cost`，但：

- 入库记录的 `project_id` 是后期才加的，历史入库没绑定项目 → 漏计；
- 入库 `unit_price` 可空，出库快照的是当时物料单价 → 两者口径不同却混在一个数里；
- 前端只有一个「物料成本」总数，说不清是采购的还是领用的，对不上账时无法排查。

### 设计

材料成本拆成两条口径，都计入总成本（HZY 要求「完整计入」），但分别展示：

```
项目材料成本 = 项目直采入库成本 + 项目领用出库成本

项目直采入库成本 = Σ (入库数量 × 入库单价)        # record_type=in 且 project_id=本项目
项目领用出库成本 = Σ (出库数量 × 出库时物料单价)   # record_type=out 且 project_id=本项目
```

单价缺失时回退到物料当前 `unit_price`，并在返回里用 `estimated_records` 标记有几条是估算的，避免"看起来精确其实是猜的"。

`GET /api/analysis/project/{id}` 的 `cost` 增加：

```jsonc
"material_cost": 123456,          // = material_cost_in + material_cost_out（兼容旧字段）
"material_cost_in": 100000,       // 项目直采入库
"material_cost_out": 23456,       // 项目领用出库
"material_cost_estimated_count": 2 // 有几条记录用了回退单价
```

> **口径提醒**：为项目专门采购入库、随后又出库到同一项目的物料，两条口径会各计一次。这是「完整计入」的直接后果，拆分展示就是为了让这种重复看得见。若后续要改成只认一条，改 `services/cost.py::project_material_cost` 的 `mode` 参数即可（`both`/`in`/`out`，默认 `both`）。

预算对比（配合需求 5）：`GET /api/analysis/project/{id}` 增加

```jsonc
"budget": { "budget_amount": 800000, "quote_amount": 950000,
            "used_amount": 612000, "usage_rate": 76.5, "over_budget": false }
```

## 2. 报销完整链路（需求 2）

### 状态机

```
pending_review（已提交/待主管审核）
   │  audit(manager, approved)
   ▼
manager_approved（主管已审）
   │  confirm-receipt  ← 硬门禁；admin 可 skip（填原因）
   ▼
receipt_confirmed（项目已收款）
   │  create-document
   ▼
document_created（单据已创建，生成单据号 BX-YYYYMMDD-XXXX）
   │  audit(finance, approved)
   ▼
finance_approved（财务已审）
   │  generate-voucher（生成凭证号 PZ-YYYYMMDD-XXXX，可挂凭证附件）
   ▼
voucher_generated（凭证已生成）
   │  pay
   ▼
paid（已付款）

任一审核环节 rejected → rejected；申请人修改后重新提交 → pending_review
```

- 每一步都是独立接口 + 独立角色校验，状态前置条件在 `services/reimburse_flow.py` 里集中声明，router 只做取数、写库、记日志。
- 老数据兼容：不引入新的终态，历史停在 `manager_approved` / `finance_approved` 的记录不会卡死——补做新增的中间步骤即可继续往下走。
- `pay` 只允许从 `voucher_generated` 进入；`generate-voucher` 允许从 `finance_approved` 进入，所以历史 `finance_approved` 记录只多一次「生成凭证」点击。

### 接口

| 方法 | 路径 | 角色 | 说明 |
|------|------|------|------|
| POST | `/api/reimbursements/{id}/confirm-receipt` | admin, finance | 确认项目收款；带 `contract_id`（甲方合同，来自 options 接口）、`receipt_amount`、`receipt_date`、`note`；admin 可传 `skip=true` + `skip_reason` |
| POST | `/api/reimbursements/{id}/create-document` | admin, finance | 生成单据号，进入财务审核 |
| POST | `/api/reimbursements/{id}/generate-voucher` | admin, finance | 生成凭证号，可上传凭证附件 |
| POST | `/api/reimbursements/{id}/audit` | admin, project_manager（主管） / admin, finance（财务） | 沿用；财务审核前置条件改为 `document_created` |
| POST | `/api/reimbursements/{id}/pay` | admin, finance | 前置条件改为 `voucher_generated` |

### 新增字段（ReimbursementModel）

| 字段 | 说明 |
|------|------|
| `receipt_contract_id` / `receipt_contract_no` | 收款对应的甲方合同 |
| `receipt_amount` / `receipt_date` / `receipt_note` | 收款金额、日期、备注 |
| `receipt_confirmed_at` / `receipt_confirmed_by` / `receipt_confirmed_by_name` | 收款确认留痕 |
| `receipt_skipped` / `receipt_skip_reason` | 管理员跳过门禁的留痕 |
| `document_no` / `document_created_at` / `document_created_by` / `document_created_by_name` | 单据 |
| `voucher_no` / `voucher_generated_at` / `voucher_generated_by` / `voucher_generated_by_name` / `voucher_files` | 凭证 |

审批日志 `audit_logs` 复用 `AuditLogMap`，新增 `audit_level` 取值：`receipt` / `document` / `voucher`，`action` 取值 `confirmed` / `created` / `generated` / `skipped`。

## 3. 权限收紧（需求 3）

集中式权限表 `backend/app/utils/permissions.py`，一处改动全站生效：

```python
PERMISSION_ROLES = {
    "project:list":      ("admin", "project_manager"),
    "project:options":   ALL_ROLES,          # 下拉选项，所有人可用
    "contract:view":     ("admin", "project_manager"),
    "contract:options":  ("admin", "project_manager", "finance", "procurement"),
    "acceptance:view":   ("admin", "project_manager"),
    "invoice:view":      ("admin", "project_manager", "finance"),
    "invoice:manage":    ("admin", "finance"),
    "reimburse:receipt": ("admin", "finance"),
    ...
}
```

`require_permission("contract:view")` 作为 FastAPI 依赖使用，语义与现有 `require_roles` 一致（403 + 中文提示）。

### 为什么要「精简选项接口」

收紧后财务看不到合同，但财务的合同付款、报销链路里的项目收款确认都要选合同；同理其他模块的项目下拉框依赖项目列表。因此拆成两个粒度：

| 接口 | 返回 | 谁能用 |
|------|------|--------|
| `GET /api/projects` | 项目全字段（客户、预算、报价、地址…） | admin、项目负责人（负责人只看自己的） |
| `GET /api/projects/options` | 仅 `project_id` + `project_name` + `status` | 所有登录用户（报销/出入库/验收的下拉框） |
| `GET /api/contracts` | 合同全字段（条款、附件、发票…） | admin、项目负责人 |
| `GET /api/contracts/options` | 合同号、名称、类型、项目、含税金额、已付金额 | admin、项目负责人、财务、采购 |

**遗留影响（需要 HZY 确认是否接受）**：采购专员保留了供应商合同的新建/编辑权限，但收紧后拿不到完整合同列表，只能通过 options 定位合同。若要让采购继续正常维护供应商合同，把 `contract:view` 改成 `("admin", "project_manager", "procurement")` 并在 router 里保留原有的「采购只看 supplier」过滤即可——一行改动。

## 4. 报销禁止新增费用大类（需求 4）

服务端校验（`create_reimbursement` / `update_reimbursement`）：

1. `expense_category_id` 必须存在于 `ReimburseCategoryModel`、`level == 1`、`is_active == True`，否则 400；
2. `expense_subcategory_id` 若传，必须存在、`parent_id == expense_category_id`、`is_active == True`，否则 400；
3. `expense_type` 由服务端派生（有子类取子类，否则取大类），**忽略前端传值**，避免绕过校验写入野值；
4. 仅传老式 `expense_type` 的历史客户端：该值必须能在分类表里查到且启用，否则 400。

分类档案的增删改本来就只有 `admin`（`require_roles("admin")`），报销页面不提供任何新建大类入口，前端 Select 不开放自由输入。

## 5. 项目看板预警 + 待办中心（需求 5、7）

### 项目完整度清单

一个项目的完整组成部分（HZY 原话）：预算、报价、合同（甲方 + 采购）、验收资料、报销、工费。加上发票（需求 6 的自然延伸）共 8 项。

`services/alerts.py::evaluate_project_checklist()` 是**纯函数**（输入普通 dict，输出结论），便于测试：

| key | 名称 | 判定完成 | 期限基准 | 负责角色 |
|-----|------|----------|----------|----------|
| `budget` | 预算 | `budget_amount > 0` | 开工 +7 天 | 项目负责人 |
| `quote` | 报价 | `quote_amount > 0` | 开工 +7 天 | 项目负责人 |
| `client_contract` | 甲方合同 | 存在 client 合同且状态 signed/fulfilled | 开工 +14 天 | 项目负责人 |
| `supplier_contract` | 采购合同 | 存在 supplier 合同（有材料成本时才必需） | 开工 +30 天 | 采购专员 |
| `labor_contract` | 工费 | 存在 construction 合同 | 开工 +30 天 | 项目负责人 |
| `acceptance` | 验收资料 | 存在验收记录且至少上传 1 份资料 | 计划完工日 | 项目负责人 |
| `invoice` | 发票 | 已开票金额 ≥ 甲方合同金额 | 计划完工日 +30 天 | 财务 |
| `reimbursement` | 报销 | 无停留超过 7 天的在途报销 | — | 当前审核人 |

每项输出：

```jsonc
{ "key": "acceptance", "label": "验收资料", "status": "overdue",
  "message": "项目已到计划完工日 30 天，验收资料仍未上传",
  "severity": "high", "due_date": "2026-07-21", "days_overdue": 30,
  "owner_role": "project_manager", "owner_id": "u001", "owner_name": "张三" }
```

`status`：`ok`（已完成）/ `missing`（未完成但未到期）/ `overdue`（已逾期）/ `warning`（有风险，如预算超支）。
项目健康度 `health_score = 完成项数 / 应完成项数 × 100`，看板用红黄绿灯呈现。

### 接口

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/alerts/board` | `alerts:board`（admin/财务/项目负责人） | 项目看板：每个项目一行 + 8 项灯色 + 健康度（项目负责人只看自己的） |
| GET | `/api/alerts/project/{project_id}` | `alerts:board` | 单项目清单明细 |
| GET | `/api/todos` | 全部角色 | **我的待办**：按当前用户角色聚合 |
| GET | `/api/todos/count` | 全部角色 | 待办数量（顶栏红点，轻量） |

看板受权限约束是因为预警文案里带预算金额、合同金额、未开票余额；待办不受约束，
因为它按用户逐条派发，只包含本职要处理的事。待办里的记录还会按可见范围过滤
（项目负责人只收到自己项目的报销/验收待办），保证"去处理"点进去一定能找到那条记录。

### 待办来源聚合

| 来源 | 给谁 | 严重度 |
|------|------|--------|
| 项目清单未完成项 | 该项的 owner（项目负责人/采购/财务）+ admin | overdue=high / missing=medium |
| 待我审核的报销（主管、财务） | 对应角色 | 停留 >7 天 high |
| 待收款确认 / 待创建单据 / 待生成凭证 / 待付款 | 财务、admin | medium |
| 验收需整改 | 项目负责人 | high |
| 库存预警（缺货/低于阈值） | 采购、仓库、admin | 缺货 high |

每条待办：`{todo_id, type, title, detail, severity, project_id, project_name, link, due_date, days_pending}`，`link` 是前端路由，点了直接跳到该干的地方。

### 前端呈现

- **工作台（项目看板）**：顶部「我的待办」卡片（按严重度排序，红/橙/蓝），下面「项目健康度看板」——每行一个项目，8 个圆点灯 + 健康度进度条，点项目名进详情；
- **待办中心 `/todos`**：完整待办列表，可按类型/严重度筛选；
- **顶栏**：待办数量红点（`/api/todos/count`），HZY 要的「上班第一件事看系统有什么没做」；
- **项目详情**：新增「完整度」Tab，逐项列出 8 项状态与逾期天数。

## 6. 发票批次管理（需求 6）

### 为什么要两层

HZY 的例子：100 万项目，甲方先要 40 万预付款发票，其中材料 30 万（税率 13%）、工费 10 万（税率 9%）→ **一个批次、两张发票**；剩下 60 万在另一个时间开 → **另一个批次**。所以「批次（一次开票行为）」和「单张发票」必须分开建模，附件挂在单张发票上。

### 数据模型

**InvoiceBatchModel（发票批次）**

| 属性 | 值 |
|------|-----|
| PK | `INVOICE_BATCH#{batch_id}` |
| SK | `META` |
| GSI1PK / GSI1SK | `INVOICE_CONTRACT#{contract_id}` / `BATCH#{issue_date}#{batch_id}` |
| GSI2PK / GSI2SK | `PROJECT#{project_id}` / `INVOICE_BATCH#{batch_id}` |

字段：`batch_id`、`batch_no`（自动 `FP-YYYYMMDD-XXXX`）、`batch_name`（如"预付款40万"）、`payment_stage`（`advance` 预付款 / `progress` 进度款 / `final` 尾款 / `other`）、`contract_id`、`contract_no`、`project_id`、`project_name`、`issue_date`、`planned_amount`（本批次计划开票额）、`total_amount_with_tax`、`total_amount_without_tax`、`total_tax_amount`、`invoice_count`（后四项由明细汇总，写入时重算）、`status`（`draft` 待开 / `issued` 已开 / `received` 甲方已收 / `void` 作废）、`remarks`。

**InvoiceRecordModel（单张发票）**

| 属性 | 值 |
|------|-----|
| PK | `INVOICE_BATCH#{batch_id}` |
| SK | `INVOICE#{invoice_id}` |
| GSI1PK / GSI1SK | `INVOICE_CONTRACT#{contract_id}` / `INVOICE#{issue_date}#{invoice_id}` |
| GSI2PK / GSI2SK | `PROJECT#{project_id}` / `INVOICE#{invoice_id}` |

字段：`invoice_id`、`batch_id`、`invoice_no`（发票号码）、`invoice_code`（发票代码）、`category`、`tax_rate`、`amount_with_tax`、`amount_without_tax`、`tax_amount`、`issue_date`、`buyer_name`、`seller_name`、`remarks`、`attachments`（发票扫描件/PDF）。

同一个 PK 下 `SK=META` 是批次本身、`SK=INVOICE#{id}` 是该批次的发票，一次 Query 取全套 —— 和现有 Material/StockRecord 的做法一致。

### 发票类别与税率

| category | 名称 | 默认税率 |
|----------|------|----------|
| `material` | 材料/货物 | 13% |
| `construction` | 施工/建筑服务 | 9% |
| `service` | 技术服务 | 6% |
| `other` | 其他 | 手填（含小规模 3% / 1% / 免税 0%） |

默认税率只是表单预填，实际以录入值为准（小规模纳税人、简易计税都可能不同）。

金额换算（`services/invoice_calc.py`，纯函数、可测）：

```
不含税 = round(含税 / (1 + 税率), 2)
税额   = round(含税 - 不含税, 2)
```

前端录入含税金额 + 税率自动算出另两项，允许手工覆盖（发票上的数字才是准的）；覆盖后校验 `|不含税 + 税额 - 含税| <= 0.02`，超出则拒绝，防止录错。

### 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/invoices/batches?contract_id=&project_id=&status=` | 批次列表（含明细） |
| POST | `/api/invoices/batches` | 建批次 |
| GET/PUT/DELETE | `/api/invoices/batches/{batch_id}` | 批次详情/改/删（删批次连带删明细） |
| POST | `/api/invoices/batches/{batch_id}/items` | 加一张发票 |
| PUT/DELETE | `/api/invoices/batches/{batch_id}/items/{invoice_id}` | 改/删单张发票 |
| GET | `/api/invoices/summary?contract_id=\|project_id=` | 开票进度：合同额、已开票、未开票、按类别/税率汇总 |

`contract.invoice_amount`（旧的单值字段）保留只读，新的汇总走 `/api/invoices/summary`，避免历史数据被覆盖。

### 前端

- 合同列表新增「发票」列 → 打开发票批次管理弹窗：批次表格（可展开看该批次的每张发票）+ 批次/发票的增删改 + 顶部开票进度条；
- 项目详情新增「发票」Tab：该项目所有批次 + 开票进度；
- 预警：甲方合同存在但未开票余额 > 0 且已过计划完工日 30 天 → 发票项亮红灯。

## 7. 测试策略

沿用 `sandbox/run_tests.sh`（后端 pytest 纯逻辑 + 前端 `tsc -b` + `vite build`）。业务判断全部下沉到不依赖 AWS 的纯函数模块，便于覆盖：

| 测试文件 | 覆盖 |
|----------|------|
| `tests/test_permissions.py` | 权限表默认值、`require_permission` 放行/拒绝、options 与 view 的粒度差异 |
| `tests/test_reimburse_flow.py` | 完整链路顺序、非法跳步被拒、admin 跳过收款、老数据兼容路径、驳回回退 |
| `tests/test_invoice_calc.py` | 各税率换算、四舍五入、手工覆盖校验、批次汇总 |
| `tests/test_alerts.py` | 8 条规则的 ok/missing/overdue 判定、期限计算、负责人归属、健康度 |
| `tests/test_cost.py` | 入库/出库成本拆分、单价回退与估算计数 |
| `tests/test_contracts.py` | 已有，保持通过 |
