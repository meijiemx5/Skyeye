# Skyeye 业务逻辑文档

> **权限的唯一权威是 `backend/app/utils/permissions.py` 里的 `PERMISSION_ROLES` 表**，
> 前端 `frontend/src/utils/permissions.ts` 是它的镜像（只用于隐藏按钮）。改权限改那一张表即可，

### 1.3 为什么有 `*:options` 这一层

「查看项目列表 / 合同 / 验收资料仅管理员与项目负责人」收紧后，财务的合同付款、报销链路的项目收款确认，
以及所有角色提交报销/出入库时的项目下拉框都会断掉。因此按数据粒度拆成两个接口：

| 接口 | 返回 | 谁能用 |
|------|------|--------|
| `GET /api/projects` | 项目全字段（客户、预算、报价、地址…） | 管理员、项目负责人（负责人只看自己的） |
| `GET /api/projects/options` | 仅 project_id + project_name + status | 全部角色 |
| `GET /api/contracts` | 合同全字段（条款、附件、付款节点…） | 管理员、项目负责人（限自己项目） |
| `GET /api/contracts/options` | 合同号、名称、类型、项目、含税金额、已付金额 | 管理员、项目负责人、财务、采购 |

> **遗留影响**：采购专员保留供应商合同的新建/编辑权限，但拿不到完整合同列表，只能靠 options 定位。
> 若要放开，把 `contract:view` 改成 `("admin", "project_manager", "procurement")` 即可（一行）。

## 2. 认证业务逻辑

### 2.1 登录流程

```
POST /api/auth/login { username, password }

1. 按用户名查找用户（Scan filter）
2. 检查账号是否被锁定
   - locked_until > 当前时间 → 返回 423 "账号已锁定"
   - locked_until < 当前时间 → 清除锁定状态
3. 检查账号是否启用
   - is_active == false → 返回 403 "账号已禁用"
4. 验证密码
   - 密码错误 → login_fail_count + 1
     - 累计 >= 3次 → 设置 locked_until = 当前 + 1小时
     - 返回 401 "用户名或密码错误"
   - 密码正确 → 重置 login_fail_count = 0, locked_until = null
5. 生成 JWT Token（有效期24小时）
   - payload: { sub: user_id, username, display_name, role }
6. 返回 { access_token, user_info }
```

### 2.2 密码管理

**用户自行修改密码：**
```
POST /api/auth/change-password { old_password, new_password }
→ 验证原密码 → 更新密码哈希 → 前端自动退出重新登录
```

**管理员重置密码：**
```
POST /api/auth/users/{user_id}/reset-password
→ 仅 admin 角色可操作
→ 重置密码为 "123456"
→ 同时清除锁定状态和失败计数
```

### 2.3 密码加密方式

```python
# 加密
salt = random_hex(16)  # 16位随机盐
hash = SHA256(salt + password)
stored = f"{salt}:{hash}"

# 验证
salt, stored_hash = stored.split(":")
input_hash = SHA256(salt + input_password)
return input_hash == stored_hash
```

## 3. 合同管理业务逻辑

### 3.1 合同类型

| 类型 | 标识 | 编号前缀 | 说明 |
|------|------|---------|------|
| 甲方合同 | `client` | JF- | 公司与客户签订的合同（收入来源） |
| 供应商合同 | `supplier` | GY- | 公司与供应商签订的采购合同（成本支出） |
| 施工合同 | `construction` | SG- | 公司与施工人员签订的施工合同（成本支出） |

### 3.2 合同编号生成规则

```
{类型前缀}-{日期YYYYMMDD}-{4位随机大写字母数字}
示例: JF-20260418-C919, GY-20260418-A3B2, SG-20260418-X1Y2
```

### 3.3 合同状态流转

```
draft（待签订）
  │
  ▼
signed（已签订）
  │
  ├──→ fulfilled（已履行）   # 正常完成
  │
  └──→ terminated（已终止）  # 异常终止
```

### 3.4 合同付款流程

合同付款采用**逐笔登记制**，仅管理员和财务人员可操作：

```
POST /api/contracts/{id}/payment
{
  amount: 5000,              // 本次付款金额（必填）
  payment_method: "bank_transfer",  // 付款方式：bank_transfer/cash/check
  payment_date: "2026-04-18",      // 付款日期（必填）
  note: "第一期付款"               // 备注
}
```

**处理逻辑：**
1. 验证付款金额 > 0
2. 创建付款节点记录（PaymentNode），状态为 "paid"
3. 累加到合同的 `paid_amount` 字段
4. 记录操作日志

**前端UI：**
- 合同列表「已付款」列显示金额 + 💲付款按钮（仅admin/finance可见）
- 点击弹出付款弹窗，显示合同金额/已付/未付汇总
- 每笔付款独立记录，可追溯

### 3.5 合同统计

系统自动统计并展示：
- 各类合同的数量、总金额
- 已付款金额、未付款金额
- 按类型分组统计
- 按状态分组统计

### 3.5 项目关联（必填）

合同新建时**必须选择关联项目**（下拉框从项目列表中选择），用于：
- 项目分析中计算收入和成本
- 按项目筛选合同
- 项目维度的数据汇总

### 3.6 合同附件管理

- 列表页「附件」列显示已上传附件数量，点击可打开独立附件管理弹窗
- 支持上传合同PDF、发票、到款截图等文件
- 可在线查看PDF/图片，可下载所有类型文件

### 3.7 角色数据过滤

| 角色 | 可见合同 |
|------|---------|
| admin | 所有合同 |
| finance | 所有合同（侧重付款数据） |
| project_manager | 仅 client 类型合同 |
| procurement | 仅 supplier 类型合同 |
| construction | 仅自己相关的 construction 合同 |

## 4. 报销业务逻辑

### 4.1 报销类型（费用分类）

费用分类是**两级档案**（`ReimburseCategoryModel`，大类 + 子类），由管理员在「报销类型管理」维护。
系统初始化时预置四个大类：`material` 物料采购、`travel` 差旅费、`equipment_rental` 设备租赁、`other` 其他。

**约束（HZY 2026-08-20）：报销环节不允许新增费用大类，只能选择系统已有的费用大类。**
服务端在 `create_reimbursement` / `update_reimbursement` 里校验：

1. `expense_category_id` 必须存在、`level == 1`、`is_active == True`，否则 400；
2. `expense_subcategory_id` 若传，必须存在、`parent_id == expense_category_id`、启用，否则 400；
3. `expense_type` **由服务端派生**（有子类取子类，否则取大类），忽略前端传值，防止绕过校验写入野值；
4. 只传老式 `expense_type` 的客户端：该值必须能在分类表里查到且启用。

分类档案的增删改本来就只有 `admin`，报销页面不提供任何新建大类入口。

### 4.2 报销状态机（完整链路）

链路：**提交报销 → 主管审核 → 项目收款 → 创建单据 → 财务审核 → 凭证生成 → 付款**

```
pending_review（待主管审核）
   │  POST /audit  (主管/admin, approved)
   ▼
manager_approved（主管已审）
   │  POST /confirm-receipt  ← 硬门禁；admin 可 skip（必填原因）
   ▼
receipt_confirmed（项目已收款）
   │  POST /create-document  → 生成单据号 BX-YYYYMMDD-XXXX
   ▼
document_created（单据已创建）
   │  POST /audit  (财务/admin, approved)
   ▼
finance_approved（财务已审）
   │  POST /generate-voucher → 生成凭证号 PZ-YYYYMMDD-XXXX
   ▼
voucher_generated（凭证已生成）
   │  POST /pay
   ▼
paid（已付款）

主管审核 / 财务审核 driven rejected → rejected（已驳回）
                                        │
                                        └─[申请人修改后重新提交]→ pending_review
```

**状态流转规则集中在 `backend/app/services/reimburse_flow.py`**，router 只负责取数、落库、留痕。
不允许跳步：状态与步骤不匹配时返回 400，并在提示里说明"下一步应为 X"。

### 4.3 各环节规则

| 环节 | 接口 | 角色 | 前置状态 | 说明 |
|------|------|------|----------|------|
| 主管审核 | `POST /{id}/audit` | project_manager, admin | `pending_review` | 通过 → `manager_approved`；驳回 → `rejected` |
| 项目收款确认 | `POST /{id}/confirm-receipt` | finance, admin | `manager_approved` | 必须选甲方合同 + 收款金额 > 0；合同号由服务端按 id 查库写入；校验合同类型为 client 且属于该报销的项目 |
| 跳过收款 | 同上，`skip=true` | admin | `manager_approved` | 必填 `skip_reason`，写入 `receipt_skipped`/`receipt_skip_reason` 与审批日志 |
| 创建单据 | `POST /{id}/create-document` | finance, admin | `receipt_confirmed` | 单据号留空自动生成 |
| 财务审核 | `POST /{id}/audit` | finance, admin | `document_created` | 通过 → `finance_approved`；驳回 → `rejected` |
| 凭证生成 | `POST /{id}/generate-voucher` | finance, admin | `finance_approved` | 凭证号留空自动生成，可挂凭证附件 |
| 付款 | `POST /{id}/pay` | finance, admin | `voucher_generated` | 需填付款金额、方式、时间 |

`/audit` 走哪一级由**当前状态**决定（不是由角色决定）：`pending_review` → 主管审核，
`document_created` → 财务审核；角色不匹配返回 403 并说明当前需要哪一级审核。

**老数据兼容**：历史停在 `manager_approved` / `finance_approved` 的记录仍在链路上，
补做新增的中间步骤即可继续往下走，不会卡死。

### 4.3.1 报销列表可见范围

| 角色 | 可见报销 |
|------|---------|
| admin / finance | 全部 |
| project_manager | 自己提交的 **+ 自己负责项目的**（后者就是他要做主管审核的那些） |
| construction | 仅自己提交的 |
| procurement / warehouse | 全部（沿用原有行为） |

> 项目负责人必须能看到自己项目上别人提交的报销，否则待办里的"待主管审核"点进去会是空列表。

### 4.4 报销修改规则

- 状态为 `pending_review`（待主管审核）或 `rejected`（已驳回）时可编辑
- 一旦进入链路（`manager_approved` 及之后，直到 `paid`）**不可编辑**
- 修改后状态自动重置为 `pending_review`，重新进入审批流程
- 只有申请人本人或 admin 角色可编辑
- 编辑时可修改：报销类型、关联项目、金额、事由、日期、凭证附件

### 4.5 报销凭证管理

- 列表页「凭证」列显示已上传凭证数量，点击可打开独立的附件管理弹窗
- 可在弹窗中查看、下载、删除凭证（仅待审核/已驳回状态可编辑）
- 每笔报销最多上传5个凭证文件

### 4.5 审核日志

每次审核操作自动记录：
- 审核人ID、姓名
- 审核时间
- 审核结果（通过/驳回）
- 审核意见
- 审核级别（manager/finance）

## 5. 验收资料业务逻辑

### 5.1 验收状态流转

```
pending_upload（待上传）
  │
  ▼
```

## 6. 库存管理业务逻辑

### 6.1 物料分类

| 标识 | 名称 | 说明 |
|------|------|------|
| `equipment` | 弱电设备 | 监控摄像头、交换机等 |
| `cable` | 线缆 | 网线、光纤、电缆等 |
| `accessory` | 配件 | 水晶头、面板、桥架等 |
| `tool` | 工具 | 测线仪、电钻等 |
| `other` | 其他 | 其他物料 |

### 6.2 入库流程

```
POST /api/inventory/stock-in
{
  material_id: "xxx",
  quantity: 100,
  unit_price: 50,
  supplier_name: "XX供应商",
  record_date: "2026-04-18"
}

处理逻辑：
1. 查找物料（Material），不存在返回 404
2. 创建入库记录（StockRecord, type="in"）
3. 更新物料库存数量: stock_quantity += quantity
4. 更新单价（取最新入库单价）
5. 更新库存状态（正常/预警/缺货）
```

### 6.3 出库流程

```
POST /api/inventory/stock-out
{
  material_id: "xxx",
  quantity: 10,
  project_id: "xxx",      # 关联项目
  project_name: "xxx",
  requester_name: "张三",
  purpose: "项目施工",
  record_date: "2026-04-18"
}

处理逻辑：
1. 查找物料，不存在返回 404
2. 检查库存是否充足: stock_quantity >= quantity
   - 不足 → 返回 400 "库存不足，当前库存: X"
3. 创建出库记录（StockRecord, type="out"）
4. 更新物料库存数量: stock_quantity -= quantity
5. 更新库存状态
```

### 6.4 盘点调整流程

```
POST /api/inventory/adjustment
{
  material_id: "xxx",
  actual_quantity: 95,       # 实际盘点数量
  adjustment_reason: "盘亏",
  record_date: "2026-04-18"
}

处理逻辑：
1. 查找物料
2. 记录差异: quantity = |actual_quantity - system_quantity|
3. 创建盘点记录（StockRecord, type="adjustment"）
   - system_quantity: 系统当前数量
   - actual_quantity: 实际数量
4. 更新物料库存: stock_quantity = actual_quantity
5. 更新库存状态
```

### 6.5 库存预警逻辑

```python
def update_stock_status(material):
    if material.stock_quantity <= 0:
        material.stock_status = "out_of_stock"  # 缺货
    elif material.min_stock_threshold and material.stock_quantity <= material.min_stock_threshold:
        material.stock_status = "warning"  # 预警
    else:
        material.stock_status = "normal"  # 正常
```

- 每次入库/出库/盘点后自动执行
- 工作台首页展示预警物料列表

## 7. 项目分析业务逻辑

### 7.1 总览分析 (GET /api/analysis/overview)

**汇总数据来源：**

```
总收入 = Σ 甲方合同金额 (contract_type == "client")
总成本 = Σ 供应商合同金额 + Σ 已付报销金额
库存总值 = Σ (物料数量 × 单价)
```

**每个项目的汇总：**
```
项目收入 = Σ 该项目甲方合同金额
项目成本 = Σ 该项目供应商合同金额 + Σ 施工合同金额 + Σ 该项目已付报销金额 + 项目材料成本
项目利润 = 项目收入 - 项目成本
利润率 = 项目利润 / 项目收入 × 100%
```

### 7.1.1 项目材料成本口径（出入库完整计入）

```
项目材料成本 = 项目直采入库成本 + 项目领用出库成本

项目直采入库成本 = Σ (入库数量 × 入库单价)        # record_type=in  且 project_id=本项目
项目领用出库成本 = Σ (出库数量 × 出库时物料单价)   # record_type=out 且 project_id=本项目
盘点(adjustment) 不计入项目成本
```

- 单价缺失时回退到物料当前 `unit_price`，并用 `material_cost_estimated_count` 标记有几条是估算的；
- 接口返回 `material_cost`（合计）、`material_cost_in`、`material_cost_out` 三个值，前端分开展示；
- `GET /api/analysis/project/{id}?material_cost_mode=both|in|out` 可切换口径，默认 `both`；
- **口径提醒**：为项目专门采购入库、随后又出库到同一项目的物料，两条口径会各计一次。
  这是"完整计入"的直接后果，拆分展示就是为了让这种重复看得见。逻辑在 `services/cost.py`。

### 7.1.2 预算对比

项目填了 `budget_amount` 后，`GET /api/analysis/project/{id}` 返回 `budget` 块：
`used_amount`（= 总成本）、`usage_rate`、`over_budget`（已超支）、`near_budget`（用到 90%~100%）。
超支和接近预算都会反映到项目看板的预算灯上。

### 7.2 单项目分析 (GET /api/analysis/project/{project_id})

**收入分析：**
- 甲方合同总额
- 已收款金额
- 未收款金额

**成本分析：**
- 供应商采购成本
- 施工人员成本
- 报销成本
- 物料消耗成本
- 各成本占比（饼图）

**利润分析：**
- 利润金额 = 甲方合同金额 - 总成本
- 利润率 = 利润 / 收入 × 100%

**付款进度：**
- 供应商已付/未付
- 施工已付/未付

**验收进度：**
- 总验收数
- 已通过/未通过/待验收

**报销汇总：**
- 总报销金额
- 已付金额 / 待处理金额
- 按报销类型分组统计

## 8. 文件上传业务逻辑

### 8.1 上传流程（Presigned URL 方式）

```
1. 前端请求上传URL
   POST /api/upload/presigned-url
   参数: file_name, file_type, entity_type, entity_id

2. 后端生成 S3 Presigned URL（1小时有效）
   S3 Key: {entity_type}/{entity_id}/{file_id}.{ext}

3. 前端直接上传文件到 S3
   PUT {presigned_url} + 文件数据

4. 前端将文件信息保存到实体
   更新合同/报销/验收的 attachments 字段
```

**优势：**
- 文件不经过 Lambda，避免超时和内存限制
- 支持最大 5GB 文件上传
- 减少 Lambda 计算成本

### 8.2 下载流程

```
1. 前端请求下载URL
   GET /api/upload/presigned-download?s3_key=xxx

2. 后端生成 S3 Get Presigned URL（1小时有效）

3. 前端打开下载URL
```

## 9. 项目完整度预警与待办中心

> 需求背景（HZY 2026-08-20）：「我一个项目他的完整组成部分包含了预算，报价，合同（甲方合同，采购合同），
> 验收资料，报销，工费……例如验收资料迟迟不上传，那么项目就会给对应的负责人提醒，某项工作未完成」；
> 「正式上线就要让他们每天第一件事就是看系统有什么事没做，只要系统上面有待办作为通知就最好」。

规则引擎在 `backend/app/services/alerts.py`，是**纯函数**（输入普通 dict、输出结论），不落库、实时计算。

### 9.1 项目完整度清单（8 项）

| key | 名称 | 判定完成 | 期限基准 | 催谁 |
|-----|------|----------|----------|------|
| `budget` | 预算 | `budget_amount > 0` | 开工 +7 天 | 项目负责人 |
| `quote` | 报价 | `quote_amount > 0` | 开工 +7 天 | 项目负责人 |
| `client_contract` | 甲方合同 | 存在 client 合同且状态 signed/fulfilled | 开工 +14 天 | 项目负责人 |
| `supplier_contract` | 采购合同 | 存在 supplier 合同（**仅当有材料成本时才必需**） | 开工 +30 天 | 采购专员 |
| `labor_contract` | 工费 | 存在 construction 合同 | 开工 +30 天 | 项目负责人 |
| `acceptance` | 验收资料 | 六类资料里至少上传 1 份（只建记录不算） | 计划完工日 | 项目负责人 |
| `invoice` | 发票 | 已开票金额 ≥ 甲方合同金额（**仅当有甲方合同金额时才必需**） | 完工 +30 天 | 财务 |
| `reimbursement` | 报销 | 无停留超过 7 天的在途报销 | — | 当前处理人 |

- 开工日缺失时退化用 `created_at`；开工日与完工日都没有时永不判逾期（只会是 `missing`）。
- 每项状态：`ok` / `missing`（未到期）/ `overdue`（已逾期，severity=high）/ `warning`（有风险，如预算超支、验收需整改）。
- 不适用项（`applicable=false`）不计入健康度：`health_score = 完成项数 / 应完成项数 × 100`。

### 9.2 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/alerts/board?project_status=active\|all` | 项目看板：每项目 8 项灯色 + 健康度 + 汇总（项目负责人只看自己的） |
| GET | `/api/alerts/project/{project_id}` | 单项目清单明细 |
| GET | `/api/todos?todo_type=&severity=` | 我的待办（`summary` 始终反映全部，不受筛选影响） |
| GET | `/api/todos/count` | 待办数量，顶栏红点用 |

### 9.3 待办来源与归属

| 来源 | 派给谁 | 严重度 |
|------|--------|--------|
| 项目清单未完成项 | 该项的 owner（项目负责人/采购/财务）+ 管理员 | overdue=high / missing=medium |
| 在途报销当前环节 | 待主管审核→项目负责人；收款/单据/审核/凭证/付款→财务 | 停留 >7 天升为 high |
| 报销被驳回 | 申请人本人 | medium |
| 验收需整改 | 项目负责人、管理员 | high |
| 库存缺货/低于阈值 | 采购、仓库、管理员 | 缺货 high，预警 medium |

排序：先按严重度，再按等待天数（久的在前）。前端呈现：工作台「我的待办」卡片 + 项目看板红黄绿灯，
待办中心页 `/todos` 看全量，左侧菜单「我的待办」带红点。

> AI 识别提交资料是否正确属于下一阶段（HZY：「初步是有，下一步就是 ai 的植入」），本期只做规则预警。

## 10. 发票分批次管理

> 需求背景（HZY 2026-08-20）：「发票不是一次性开具，是分批次的，而且一次开具的发票有可能是多张」；
> 「100 万的项目，甲方要求先开 40 万预付款，剩下 60 万一定是在另一个时间开」；
> 「刚才那 40 万发票，有 30 万是材料，有 10 万是工费，那么一定是两张发票」。

### 10.1 两层模型

- **批次（InvoiceBatch）**= 一次开票行为，如"预付款40万"，挂在某个合同上；
- **单张发票（InvoiceRecord）**= 批次下的每一张票，各自有类别、税率、金额、扫描件。

所以 HZY 的例子是：批次「预付款40万」下两张发票（材料 30 万 @13%、工费 10 万 @9%），
「尾款60万」是另一个批次。

### 10.2 发票类别与税率

| category | 名称 | 默认税率 |
|----------|------|----------|
| `material` | 材料/货物 | 13% |
| `construction` | 施工/建筑服务 | 9% |
| `service` | 技术服务 | 6% |
| `other` | 其他 | 手填（小规模 3% / 1% / 免税 0%） |

默认税率只是表单预填，实际以录入值为准。税率**以小数存储**（13% → 0.13），
入参接受 `13` 或 `0.13`（`>= 1` 视为百分数，所以 `1` 表示 1% 而不是 100%）。

金额换算（`services/invoice_calc.py`）：

```
不含税 = round(含税 / (1 + 税率), 2)
税额   = round(含税 - 不含税, 2)
```

允许手工覆盖不含税/税额（发票上印的数字才是准的），覆盖后校验
`|不含税 + 税额 − 含税| ≤ 0.02`，超出则拒绝，防止录错。

### 10.3 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/invoices/batches?contract_id=&project_id=&status=` | 批次列表（含明细，最新在前） |
| POST | `/api/invoices/batches` | 建批次，可在同一请求里带 `invoices` 一起提交 |
| GET/PUT/DELETE | `/api/invoices/batches/{batch_id}` | 批次详情 / 改 / 删（删批次连带删明细） |
| POST | `/api/invoices/batches/{batch_id}/items` | 加一张发票 |
| PUT/DELETE | `/api/invoices/batches/{batch_id}/items/{invoice_id}` | 改 / 删单张发票 |
| GET | `/api/invoices/summary?contract_id=\|project_id=` | 开票进度 + 按类别/税率汇总 |

批次上的 `total_*` 与 `invoice_count` 全部由明细汇总，每次明细变化后重算；`void` 批次不计入进度。
`contract.invoice_amount`（旧的单值字段）保留只读，新的汇总一律走 summary 接口，避免历史数据被覆盖。

### 10.4 前端入口

- 合同管理「发票」列 → 发票批次管理弹窗（开票进度条 + 批次表格，展开看每张发票）；
- 项目详情「发票开票」页签 → 该项目整体开票进度 + 按类别汇总，可进同一个弹窗管理；
- 未开票余额过了完工期 +30 天仍未清零 → 项目看板发票项亮红灯。
