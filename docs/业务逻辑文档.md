## 2. 认证业务逻辑

### 2.1 登录流程

```
POST /api/auth/login { username, password }

1. 按用户名查找用户（Scan filter）
2. 检查账号是否被锁定
   - locked_until > 当前时间 → 返回 423 "账号已锁定"
   - locked_until < 当前时间 → 清除锁定状态
3. 检查账号是否启用
   - is_active == false → 返回 403 "账号已禁用"
4. 验证密码
   - 密码错误 → login_fail_count + 1
     - 累计 >= 3次 → 设置 locked_until = 当前 + 1小时
     - 返回 401 "用户名或密码错误"
   - 密码正确 → 重置 login_fail_count = 0, locked_until = null
5. 生成 JWT Token（有效期24小时）
   - payload: { sub: user_id, username, display_name, role }
6. 返回 { access_token, user_info }
```

### 2.2 密码管理

**用户自行修改密码：**
```
POST /api/auth/change-password { old_password, new_password }
→ 验证原密码 → 更新密码哈希 → 前端自动退出重新登录
```

**管理员重置密码：**
```
POST /api/auth/users/{user_id}/reset-password
→ 仅 admin 角色可操作
→ 重置密码为 "123456"
→ 同时清除锁定状态和失败计数
```

### 2.3 密码加密方式

```python
# 加密
salt = random_hex(16)  # 16位随机盐
hash = SHA256(salt + password)
stored = f"{salt}:{hash}"

# 验证
salt, stored_hash = stored.split(":")
input_hash = SHA256(salt + input_password)
return input_hash == stored_hash
```

## 3. 合同管理业务逻辑

### 3.1 合同类型

| 类型 | 标识 | 编号前缀 | 说明 |
|------|------|---------|------|
| 甲方合同 | `client` | JF- | 公司与客户签订的合同（收入来源） |
| 供应商合同 | `supplier` | GY- | 公司与供应商签订的采购合同（成本支出） |
| 施工合同 | `construction` | SG- | 公司与施工人员签订的施工合同（成本支出） |

### 3.2 合同编号生成规则

```
{类型前缀}-{日期YYYYMMDD}-{4位随机大写字母数字}
示例: JF-20260418-C919, GY-20260418-A3B2, SG-20260418-X1Y2
```

### 3.3 合同状态流转

```
draft（待签订）
  │
  ▼
signed（已签订）
  │
  ├──→ fulfilled（已履行）   # 正常完成
  │
  └──→ terminated（已终止）  # 异常终止
```

### 3.4 合同付款流程

合同付款采用**逐笔登记制**，仅管理员和财务人员可操作：

```
POST /api/contracts/{id}/payment
{
  amount: 5000,              // 本次付款金额（必填）
  payment_method: "bank_transfer",  // 付款方式：bank_transfer/cash/check
  payment_date: "2026-04-18",      // 付款日期（必填）
  note: "第一期付款"               // 备注
}
```

**处理逻辑：**
1. 验证付款金额 > 0
2. 创建付款节点记录（PaymentNode），状态为 "paid"
3. 累加到合同的 `paid_amount` 字段
4. 记录操作日志

**前端UI：**
- 合同列表「已付款」列显示金额 + 💲付款按钮（仅admin/finance可见）
- 点击弹出付款弹窗，显示合同金额/已付/未付汇总
- 每笔付款独立记录，可追溯

### 3.5 合同统计

系统自动统计并展示：
- 各类合同的数量、总金额
- 已付款金额、未付款金额
- 按类型分组统计
- 按状态分组统计

### 3.5 项目关联（必填）

合同新建时**必须选择关联项目**（下拉框从项目列表中选择），用于：
- 项目分析中计算收入和成本
- 按项目筛选合同
- 项目维度的数据汇总

### 3.6 合同附件管理

- 列表页「附件」列显示已上传附件数量，点击可打开独立附件管理弹窗
- 支持上传合同PDF、发票、到款截图等文件
- 可在线查看PDF/图片，可下载所有类型文件

### 3.7 角色数据过滤

| 角色 | 可见合同 |
|------|---------|
| admin | 所有合同 |
| finance | 所有合同（侧重付款数据） |
| project_manager | 仅 client 类型合同 |
| procurement | 仅 supplier 类型合同 |
| construction | 仅自己相关的 construction 合同 |

## 4. 报销业务逻辑

### 4.1 报销类型

| 标识 | 名称 | 说明 |
|------|------|------|
| `material` | 物料采购 | 项目物料采购费用 |
| `travel` | 差旅费 | 施工人员差旅费 |
| `equipment_rental` | 设备租赁 | 设备租赁费用 |
| `other` | 其他 | 其他报销费用 |

### 4.2 报销状态机

```
pending_review（待审核）
  │
  ├──[主管/admin 审核通过]──→ manager_approved（主管已审）
  │                              │
  │                              ├──[财务/admin 审核通过]──→ finance_approved（财务已审）
  │                              │                              │
  │                              │                              └──[财务/admin 付款]──→ paid（已付款）
  │                              │
  │                              └──[财务/admin 驳回]──→ rejected（已驳回）
  │
  └──[主管/admin 驳回]──→ rejected（已驳回）
                              │
                              └──[申请人修改后重新提交]──→ pending_review（待审核）
```

### 4.3 审核规则

1. **第一级审核（主管审核）**
   - 角色要求：`project_manager` 或 `admin`
   - 条件：报销状态为 `pending_review`
   - 审核通过 → 状态变为 `manager_approved`
   - 审核驳回 → 状态变为 `rejected`

2. **第二级审核（财务审核）**
   - 角色要求：`finance` 或 `admin`
   - 条件：报销状态为 `manager_approved`
   - 审核通过 → 状态变为 `finance_approved`
   - 审核驳回 → 状态变为 `rejected`

3. **付款操作**
   - 角色要求：`finance` 或 `admin`
   - 条件：报销状态为 `finance_approved`
   - 需填写：付款金额、付款方式（银行转账/现金）、付款时间
   - 付款成功 → 状态变为 `paid`

### 4.4 报销修改规则

- 状态为 `pending_review`（待审核）或 `rejected`（已驳回）时可编辑
- 状态为 `manager_approved`（主管已审）、`finance_approved`（财务已审）、`paid`（已付款）时**不可编辑**
- 修改后状态自动重置为 `pending_review`，重新进入审批流程
- 只有申请人本人或 admin 角色可编辑
- 编辑时可修改：报销类型、关联项目、金额、事由、日期、凭证附件

### 4.5 报销凭证管理

- 列表页「凭证」列显示已上传凭证数量，点击可打开独立的附件管理弹窗
- 可在弹窗中查看、下载、删除凭证（仅待审核/已驳回状态可编辑）
- 每笔报销最多上传5个凭证文件

### 4.5 审核日志

每次审核操作自动记录：
- 审核人ID、姓名
- 审核时间
- 审核结果（通过/驳回）
- 审核意见
- 审核级别（manager/finance）

## 5. 验收资料业务逻辑

### 5.1 验收状态流转

```
pending_upload（待上传）
  │
  ▼
uploaded（已上传）
  │
  ▼
pending_acceptance（待验收）
  │
  ├──→ accepted（已验收）    # result = "passed"
  │
  └──→ needs_rectification（需整改）  # result = "failed"
         │
         └──[整改完成后]──→ pending_acceptance（待验收）
```

### 5.2 资料分类

| 分类 | 字段名 | 包含内容 |
|------|--------|---------|
| 基础验收资料 | basic_docs | 验收申请表、通知书、签字确认文件 |
| 工程类资料 | engineering_docs | 施工图纸、施工记录、设备调试报告 |
| 合规类资料 | compliance_docs | 甲方确认单、资质证明、安全验收记录 |
| 验收结果资料 | result_docs | 验收报告、签字文件 |
| 其他资料 | other_docs | 复盘报告、甲方反馈 |
| 整改反馈资料 | rectification_docs | 整改反馈材料 |

### 5.3 验收小组

每个验收记录可包含多个验收小组成员：
- 姓名、职务、联系方式

## 6. 库存管理业务逻辑

### 6.1 物料分类

| 标识 | 名称 | 说明 |
|------|------|------|
| `equipment` | 弱电设备 | 监控摄像头、交换机等 |
| `cable` | 线缆 | 网线、光纤、电缆等 |
| `accessory` | 配件 | 水晶头、面板、桥架等 |
| `tool` | 工具 | 测线仪、电钻等 |
| `other` | 其他 | 其他物料 |

### 6.2 入库流程

```
POST /api/inventory/stock-in
{
  material_id: "xxx",
  quantity: 100,
  unit_price: 50,
  supplier_name: "XX供应商",
  record_date: "2026-04-18"
}

处理逻辑：
1. 查找物料（Material），不存在返回 404
2. 创建入库记录（StockRecord, type="in"）
3. 更新物料库存数量: stock_quantity += quantity
4. 更新单价（取最新入库单价）
5. 更新库存状态（正常/预警/缺货）
```

### 6.3 出库流程

```
POST /api/inventory/stock-out
{
  material_id: "xxx",
  quantity: 10,
  project_id: "xxx",      # 关联项目
  project_name: "xxx",
  requester_name: "张三",
  purpose: "项目施工",
  record_date: "2026-04-18"
}

处理逻辑：
1. 查找物料，不存在返回 404
2. 检查库存是否充足: stock_quantity >= quantity
   - 不足 → 返回 400 "库存不足，当前库存: X"
3. 创建出库记录（StockRecord, type="out"）
4. 更新物料库存数量: stock_quantity -= quantity
5. 更新库存状态
```

### 6.4 盘点调整流程

```
POST /api/inventory/adjustment
{
  material_id: "xxx",
  actual_quantity: 95,       # 实际盘点数量
  adjustment_reason: "盘亏",
  record_date: "2026-04-18"
}

处理逻辑：
1. 查找物料
2. 记录差异: quantity = |actual_quantity - system_quantity|
3. 创建盘点记录（StockRecord, type="adjustment"）
   - system_quantity: 系统当前数量
   - actual_quantity: 实际数量
4. 更新物料库存: stock_quantity = actual_quantity
5. 更新库存状态
```

### 6.5 库存预警逻辑

```python
def update_stock_status(material):
    if material.stock_quantity <= 0:
        material.stock_status = "out_of_stock"  # 缺货
    elif material.min_stock_threshold and material.stock_quantity <= material.min_stock_threshold:
        material.stock_status = "warning"  # 预警
    else:
        material.stock_status = "normal"  # 正常
```

- 每次入库/出库/盘点后自动执行
- 工作台首页展示预警物料列表

## 7. 项目分析业务逻辑

### 7.1 总览分析 (GET /api/analysis/overview)

**汇总数据来源：**

```
总收入 = Σ 甲方合同金额 (contract_type == "client")
总成本 = Σ 供应商合同金额 + Σ 已付报销金额
库存总值 = Σ (物料数量 × 单价)
```

**每个项目的汇总：**
```
项目收入 = Σ 该项目甲方合同金额
项目成本 = Σ 该项目供应商合同金额 + Σ 施工合同金额 + Σ 该项目已付报销金额
项目利润 = 项目收入 - 项目成本
利润率 = 项目利润 / 项目收入 × 100%
```

### 7.2 单项目分析 (GET /api/analysis/project/{project_id})

**收入分析：**
- 甲方合同总额
- 已收款金额
- 未收款金额

**成本分析：**
- 供应商采购成本
- 施工人员成本
- 报销成本
- 物料消耗成本
- 各成本占比（饼图）

**利润分析：**
- 利润金额 = 甲方合同金额 - 总成本
- 利润率 = 利润 / 收入 × 100%

**付款进度：**
- 供应商已付/未付
- 施工已付/未付

**验收进度：**
- 总验收数
- 已通过/未通过/待验收

**报销汇总：**
- 总报销金额
- 已付金额 / 待处理金额
- 按报销类型分组统计

## 8. 文件上传业务逻辑

### 8.1 上传流程（Presigned URL 方式）

```
1. 前端请求上传URL
   POST /api/upload/presigned-url
   参数: file_name, file_type, entity_type, entity_id

2. 后端生成 S3 Presigned URL（1小时有效）
   S3 Key: {entity_type}/{entity_id}/{file_id}.{ext}

3. 前端直接上传文件到 S3
   PUT {presigned_url} + 文件数据

4. 前端将文件信息保存到实体
   更新合同/报销/验收的 attachments 字段
```

**优势：**
- 文件不经过 Lambda，避免超时和内存限制
- 支持最大 5GB 文件上传
- 减少 Lambda 计算成本

### 8.2 下载流程

```
1. 前端请求下载URL
   GET /api/upload/presigned-download?s3_key=xxx

2. 后端生成 S3 Get Presigned URL（1小时有效）

3. 前端打开下载URL
```
